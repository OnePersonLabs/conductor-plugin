# Inspect and migrate an existing workflow

Use before applying repository workflow setup or migration. Use existing native
inspection and configuration tools; this procedure adds no scheduler, registry,
permanent audit service or second task ledger.

## Recover the current operating path

Inspect the effective global instruction file and workflow policy for each
target home, applicable parent/root/nested repository instructions, local skill
directories, enabled plugin skills, activation metadata, routed references,
hooks, configuration layers and the current work entrance. Distinguish installed,
enabled, discoverable and session-loaded state. A directory listing or cache is
not evidence of effective activation; report incomplete inventory as unknown.

Find current issues, boards, labels, milestones, plans, task files, specifications,
decision records, checkpoints and unfinished migrations. Identify each artifact's
actual owner and consumer. Read current remote state before proposing writes.
Preserve accepted requirements, dependencies, priorities, evidence, failed
hypotheses, cumulative budgets, paused work and delivery boundaries.

Compare semantic instructions, not just names. Look for competing tracker,
meaning or checkpoint ownership; conflicting branch, commit, publication, review,
testing, delegation and resumption rules; automatic setup or skill chaining;
obsolete commands; and duplicate or misleading work entrances. Different names
can impose the same responsibility. Shared subject matter alone is not a conflict.

Trace both directions through the skill set. For a proposed disable or removal,
identify required companions, direct callers, conditional routes and examples.
Assess whether each companion still serves an independent purpose. Do not leave
an active router directing agents into the retired workflow, and do not retire
useful specialists solely because they share a package. Verify supported controls
and effective scope before promising selective disablement. Never patch installed
caches as configuration.

## Present decisions with enough context

Group connected findings by the decision that resolves them. Explain what each
tool currently makes an agent do, why that conflicts with the intended workflow,
and what capability each resolution retains or loses. Quote the complete relevant
instruction wording and identify its source when explaining a conflict. Distinguish
confirmed facts, inference and unknowns. Do not ask users to choose unexplained
skill names or remember past implementation details.

For each material issue, present the three strongest viable resolutions, recommend
one and allow the user to specify another direction. Prefer disabling a redundant
or competing route before introducing a replacement. If fewer than three viable
resolutions exist, explain that limit rather than inventing filler options.
Include consequential alternatives such as retaining independent specialists,
disabling the whole conflicting package, or integrating unique value into an
existing owner when the evidence supports them.

Briefly explain that these are the agent's best assessment and unforeseen effects
remain possible. List only non-trivial concerns that could change the decision,
especially effects difficult to reverse, notice promptly or attribute to the
choice. Do not repeat obvious consequences or generic caution. An empty concerns
list is preferable to warnings the person will learn to skim.

Record settled choices and the source-to-destination mapping in the existing
issue or checkpoint. Reuse prior authorization and keep unresolved decisions
distinct from approved work. A recommendation is not the user's decision.

## Block unresolved conflicts

Do not proceed with migration while material conflicts lack a resolution.
Continue useful inspection and preparation that does not execute the blocked
transition. Do not use another instruction to silently counterweight the conflict.

If the user asks to proceed despite an unresolved conflict whose consequences
materially change the setup, state the conflict, concrete consequences, and
recommended resolution before applying the affected changes. Continue only
after the user explicitly resolves that choice; do not add a confirmation step
for resolved or routine choices. Higher-priority restrictions still apply, and
an accepted exception remains an exception rather than a conflict-free result.

## Complete the transition

Prepare and verify a complete source-to-consumer cutover. Move actionable work
to the selected tracker, accepted meaning/evidence to its owner and active work/
recovery to one concise checkpoint. Reconcile existing remote issues before
creation. Keep future work broad and preserve complete acceptance obligations.

Migrate callers, native configuration and persistent data where required. Remove
superseded instructions, duplicate backlogs, orphan routers, obsolete commands
and replaced integration files. Follow the chosen retention policy: Git history
can preserve a removed workflow; leaving a dormant copy in the active repository
is not a clean removal. Preserve necessary evidence with clear historical scope.
Keep recovery backups outside active repositories.

Reinspect the effective instruction system after changes. Walk through ordinary
work selection, bounded implementation, verification/delivery and interrupted-work
resumption using real project records. Verify disabled and retired routes are no
longer effective, surviving callers resolve and retained obligations are covered.
Report configured, verified and session-loaded state separately. Do not claim
behavioral or human-comprehension proof from prose review, and do not add skill
invocation tests or AI evaluations without explicit authorization.
